# 数量、身份与调配契约

候选：`B01-candidate-7`。本文件是待复核的数据设计，不是已实现计算器。关联 `P0-01/P0-03`、`F03`、`S09/S10/S11/S12` 和 `D12/D13/D14`。

## 已确认规则及其字段映射

- Recipe 的原始单份重量取选中版本的明细克数合计，不取已调整量或 `serving` 数字；公共来源初始总重量从 100g 起步。
- Ingredient 的营养定义为每 100g；用户另外确认默认加入 100g。首次加入不显示直接输入控件；原始单份保存为 `originalPortionWeight=100`，随后只通过固定滑块调总量。
- 一组的 `sourceCount=N` 为正整数。`anchorWeight=originalPortionWeight*N`，滑块范围为 `[max(0,anchorWeight-100),anchorWeight+100]`；不会因反复拖动或重新打开而扩大。
- `requestedWeight` 是组的总量请求，不乘 N；`actualWeight` 是求解后真实食材合计。不可达时先显示实际值和偏差，用户明确应用后才使用实际值。
- 减一份扣原始单份，N 变为零才删除整组；扣减负值仅按已确认例外归零。对应的增份设计为 N 加一、总量请求加原始单份，保留已有微调差；它属于本批数据映射候选，尚未实施。
- 原始 300g×2，锚点600g，滑块500～700g；调整700g后减一份得到400g×1，范围200～400g。不能扣平均350g。
- 原始100g×2调到100g，减一份后保留0g×1；0≤重量<1g红框无效，可继续滑动。保存必须定位无效组并阻止事务，所有组至少1g且其他校验通过才可保存。
- `MealDraft` 可以保留0≤重量<1g和未完成预览。正式 `MealRecord` 不接受这些无效条目；不能通过导入、恢复或同步绕过保存条件。
- 1g门槛按未舍入的数值判断；0.999g不能因界面显示舍入为1.0g而通过保存。1g是整条配餐条目的总重门槛，不要求Recipe中的每个组成食材都至少1g。
- 首版配餐的调整入口和正式快照只支持 `mode=weight`，与固定重量滑块一致。旧接口中的 `energy` 属于后续纯计算能力；未开放热量求解UI，不扩展本批meal schema。

## 库记录与配餐身份

库记录身份和配餐中的重复来源键：

```text
(originNamespace, libraryEntryId, kind)
```

每份库记录独立存在；正文ID、名称或文件hash相同不自动合并、删除或隐藏。配餐里重复选择同一库记录，才增加该组sourceCount并显示xN。两条不同库记录各加入一次，即使文件字节完全一致，也保留两组x1；不能因内容相同变成一组x2。配餐行自身的entryId与libraryEntryId含义不同。

`sourceRevision/sourceContentHash/originalPortionWeight/portionBasisHash`用于核验该次加入的定义与原始基准，不是跨库条目合并键。`portionBasisHash`绑定原始明细、计量状态、营养取数、锁定和边界等不可变输入，不含当前微调、份数、显示名称或目标。其版本化确定性编码留B03；文件字节hash与计算基准hash不混用。

用户已明确同一Recipe更新自动替换库当前正文、已保存配餐及活动草稿里的对应配方，并重新计算营养，无需逐份确认，不保留可浏览旧版。“新旧版本自动分条”候选撤回。sourceRevision/sourceContentHash/portionBasisHash和源快照随成功更新一并切换；不能在一组内混用新旧基准，也不把其他独立库记录合入此组。

为了避免一个组出现两种原始单份，本候选不支持在加入页自定义另一个初始克数。若以后增加该入口，必须重新确认合并、减份和锚点规则。

## 原始基准与有界计算

Recipe 先从单份不可变快照构成 N 份原始基准：每项原始重量、显式上下界乘 N；锁定项保持该原始聚合克数。当前目标从该基准重新求解，不能再次对调整后明细乘 N。默认保护边界为单份原始0～2倍后再聚合；显式边界优先，不能因 N 改变而解锁食材。

Ingredient 按 `per100*actualWeight/100` 线性计算，不调用 Recipe 的 healthWeight 重分配。对于0≤重量<1g，仅存无效草稿请求；不伪造一份有效食材结果。

重量请求范围与可达范围分别保留。存在锁定或上下界时，滑块内的请求也可能不可达；范围不自动扩张。状态保留 `exact/approximate/unreachable/invalid`，不把无效或不可达称为达标。

删除一份后按新的原始基准重新计算；若因锁定约束不能达到扣减后的请求，保留请求与不可达预览，显式应用实际结果。不能改变锁定食材来凑齐总量。全零、未知、异常大值、重复事件和进程恢复均列入后续 B03 测试，不声称本轮已运行计算。

## 校验与历史

- Schema 校验类型、基本范围和快照必填；语义校验核对 count、原始份量、锚点、实际总量、源 hash、目标及组身份的一致性。
- 同日期与稳定餐次 ID 仅一份有效记录；冲突副本单独存放，不伪装成另一份日历配餐。
- 本地和同步将一个组的原始基准、N、请求、实际、锁定和算法版本作为完整候选提交，不逐字段合并。
- 取消预览不修改草稿，取消导入不改正式记录。快照表示该记录当前已应用的源版本，在一个revision内作为计算输入固定；成功自动更新会整体替换来源快照和派生结果，不再永久保存旧Recipe配方。目标与餐次快照仍保留。

## 自动替换、保重与异常边界

- 正常更新按完整(originNamespace,libraryEntryId,kind=recipe)定位，保留entryId、mealId/draftId、sourceCount、日期、餐次、目标和锁定状态；新版食材、per100、foodState、边界和healthWeight作为新的计算输入。锁定配餐的自动维护不等于解锁用户编辑；配方内locked食材按新版基准处理，不能为凑目标擅自解锁。
- 已保存记录和活动草稿都更新。先读取当前记录与预期revision，生成完整新候选，重算明细及组/餐营养后再条件提交；活动编辑或旧预览同时变化时重读并重新计算，不覆盖用户刚刚调整的量或套用旧预览。原地修改快照但保留旧营养不允许。
- 新版下载/校验/计算/提交失败时保留上一致状态及可恢复任务，不能宣称更新成功，也不建立可浏览的旧版本列表。有效范围内求解失败或有效范围为空时不得伪造实际值、扩大范围、违反locked或写入无效配餐。已有冲突副本按同步协议保留，不能借自动替换删除私人并发改动。
