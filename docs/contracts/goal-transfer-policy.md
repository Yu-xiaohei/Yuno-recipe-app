# 目标与导入导出契约

候选：`B01-candidate-7`；任务：`P0-04`；关联 `F05/F06`、`S14/S15/S16/S21/S22`。本文件规定待实现接口和验证边界，不表示目标计算、导入事务或导出已运行。

## 目标与餐次

[goal.schema.json](../../schemas/goal.schema.json) 定义 `GoalProfile`：`schemaVersion=1`、`kind=goalProfile`、稳定 id、revision、updatedAt、`rulesVersion=goal-status-v1`、dailyGoals 和 mealSlots。`$defs/goalMap` 可供配餐目标快照引用，快照同时保存当时 profile ID、revision 和规则版本。

指标单位固定：weight/carb/protein/fat/fiber 为 g，energy 为 kcal，vitaminC/sodium 为 mg。dailyGoals 缺少某指标表示未配置；空对象合法，不能注入 Figma 演示数字。配置值不能用 null 代替，实际营养的 null 则保留未知并显示中性。

三个目标类型只接受该类型的字段，避免隐藏旧字段继续参与计算：

| mode | 数据约束 | 判定规则 |
|---|---|---|
| target | target>0 | 相对差≤10%达标，>10%且≤20%警告，>20%超差 |
| range | 0≤lower<upper | 区间内达标；区间外到最近边界距离除以 `max(upper-lower,(upper+lower)/2)`，≤10%警告，超过为超差 |
| max | upper≥0 | 实际≤upper达标；upper>0且超出≤10%警告，超过为超限；upper=0时实际0达标，正数超限，不做除零 |

`warningFraction` 缺省按0.1解释，当前配置版本只允许0.1；Schema 的 default 不会自行填入数据。target 的20%边界和其他状态阈值由 `goal-status-v1` 定义，不是医学结论，修改须同步规则版本、文案及测试。

首次创建早餐、午餐、晚餐的已确认名称和稳定内部 ID，不同时生成推荐营养目标。用户可增删、改名、排序或停用餐次；改名、排序和停用不改 id，也不重写历史。Schema 允许空模板列表；没有可用餐次时不能伪造一餐。模板的增删操作与历史显示分开处理。

allocationWeight 是分配比例而非三大营养供能比。仅在启用餐次中归一化；执行分配时权重之和必须大于0，否则拒绝该分配操作并保留编辑态。dailyGoals 的各目标值或边界按 `allocationWeight/sum(weights)` 分配。某餐 `mealGoals` 中出现的指标为显式手动覆盖，未出现的指标继承分配；显示手动覆盖及餐次合计与日目标差额，用户主动重分配前不覆盖。没有日目标时不能根据比例生成数值。

2026-10-30用户指定沿用Figma预设，已只读核对菜单文字及截图；机器来源存入`config/development-baseline.json`的`data.mealAllocationPresets`。默认仍为早餐/午餐/晚餐，比例使用设计当前显示的2:4:4，不采用均分。按餐次当前顺序对应比例，不能擅自命名新增的第四/第五餐。

| 餐数 | 可选比例（按设计顺序） | Figma节点 |
|---|---|---|
| 2 | 5:5、4:6、3:7、6:4；自定义 | `438:3046` |
| 3 | 2:4:4、3:4:3、2:5:3、3:3:4、4:4:2；自定义 | `438:3021` |
| 4 | 2:3:3:2、2:4:3:1、3:3:3:1、3:3:1:3、4:1:4:1；自定义 | `438:2971` |
| 5 | 2:2:2:2:2；自定义 | `438:2996` |

当前三餐值节点`438:2483`明确显示2:4:4。Figma总餐数菜单还含1餐，保持单餐比例1及已有自定义能力，不将此预设列表解释为最多只能5餐。切换比例或餐数先预览，保留已有餐次稳定ID和手动覆盖，不静默重分配或改写历史快照；新增用户可见餐次名称仍由用户决定。

分配提交前还要逐餐验证最终有效目标，包括显式手动覆盖。非负比例允许暂存0，但若0权重派生出 `target=0` 或 `range=[0,0]`，且没有合法手动覆盖，则这些目标不符合既有目标契约：拒绝本次分配，保留原配置和编辑态。不能静默跳过该餐、变成未配置、修改比例或写入非法快照。`max upper=0` 仍合法；本规则不取消零上限支持。该失败路径沿用“无效目标拒绝保存”，不新增推荐值。

Schema 检查形状、非负值、单位、类型与规则版本；`lower<upper`、餐次 id/order 唯一、比例合计、继承/覆盖结果和历史不重算需要语义层验证。本轮没有实现这些计算，不以 Schema 通过代替其测试。

## 导入的两层验证

首版范围已调整：普通用户仅开放配餐备份`mealBackup`导入导出；Recipe/Ingredient本地`libraryImport`仅在开发者模式测试备用，导入后暂不能删除。Schema保留库导入格式是测试契约，不代表正式用户功能。设置、文件分派、深链、预览及提交均检查开发者能力；关闭模式后旧预览不能提交，也不能因关闭模式或清缓存删除测试库记录。配餐备份中的内嵌来源快照不自动创建库条目。以下逐条校验、8/10有效提交和事务回滚同时适用于其获准入口。

[transfer.schema.json](../../schemas/transfer.schema.json) 的根入口只识别 `schemaVersion=1` 的 `mealBackup` 或 `libraryImport` envelope。`records` 保留原始元素，即使某元素不是对象；否则两条错误记录会先使整包失败，无法执行用户已确认的“预览后只导入八条有效记录”。**根入口通过只表示包可识别，不表示记录可以落库。**

1. 在 JSON 解析前限制输入为10 MiB；超过则拒绝。拒绝重复键、NaN/Infinity、损坏 JSON、未知高版本、未知 kind 和超出实现数值范围的值。`records` 与 `goalProfiles` 合计最多10000项；Schema 各数组的上限不能代替合计检查。这些是候选工程保护上限，不是新增功能命名。
2. `mealBackup.records` 逐条用 [meal.schema.json](../../schemas/meal.schema.json) 校验正式记录/删除标记；可选 goalProfiles 逐条用 goal schema 校验。libraryImport 逐条按显式 kind 识别 Recipe/Ingredient；旧 v2 Recipe 的无 kind 输入只能进入既定 legacy 识别与迁移暂存，不能推断为 Ingredient 或自动发布。
3. 做语义和跨记录检查：日期与餐次、快照完整性、至少1g、数量原始基准、同一稳定库身份的内容冲突、不同配餐ID同日期餐次冲突、目标引用、目录身份及来源hash。不同库记录的同名/同正文ID/同hash不是自动去重或拒绝条件。旧文件需要迁移时列出差异，原件只读。
4. 每条记录保留稳定的源索引、有效/无效结果和错误字段/原因。未知或无效记录不静默丢弃；预览取消零持久化写入，不能先写 staging 到正式库再称为取消。
5. 提交仅包含有效且冲突选择已完成的记录。被选记录引用的目标或其他依赖无效时，将该条也列为无效；不能导入悬空引用。独立有效记录不因不相关的错误条目被拒绝。
6. 至少一条有效记录才能提交；提交前检查原始文件 hash、预览令牌和数据库 revision，防止文件/本地记录在预览后变化。变更则重新预览，不能沿用旧确认。
7. 用户确认后，所有选中的有效记录、目标及同步 outbox 在一个本地事务内提交；任一写入失败全部回滚。10条中2条错误时，预览列明两条原因，确认后一次性提交其余8条。不能把“允许部分无效”误写成“提交失败允许部分落库”。

导入的重复/冲突处理不能默认最后写入覆盖。具体需要用户选择的动作由既有 S21/S20 交互承担；没有已确认的用户可见名称时保留内部动作 ID，不能把文稿用途说明直接变成发布文案。系统文件选择器取消不修改数据，不默认索取全部存储权限。

库导入为每个源记录保留独立身份，缺少libraryEntryId时在预览按源索引分配并绑定token；即使两条字节hash完全一致也不合并。相同operationId重试复用同一预览身份，幂等不等于按内容去重。

## 导出与严格入口

导出只读所选范围的已验证正式配餐快照；不能导出0≤重量<1g草稿、待求解预览或未解决冲突作为正式记录。配餐内的目标快照始终随记录导出；可选 goalProfiles 是用户明确选择的本地模板，既不代表自动恢复成当前目标，也不增加 WebDAV 全局目标同步。

严格导出入口为 `transfer.schema.json#/$defs/validatedMealBackup`，要求 records 每条匹配 meal schema，可选模板匹配 goal schema。正式记录的语义校验仍需执行。序列化必须用显式字段白名单，从配餐/目标模型读取；不能序列化完整设置、凭据存储、网络客户端或数据库诊断对象。密码、token、AccessKey、credentialHandle、设备私钥、服务器配置和日志均排除。

payload/record 的 hash 不嵌入被 hash 的同一文件；导出文件可在外部回执记录字节 SHA-256。导出的是读取事务时当前已应用的Recipe/Ingredient快照、单位、来源、目标规则版本及数量语义，不能在序列化时临时拼接新库正文与旧营养。导入接收一致快照后，若关联公共Recipe/Ingredient已有经核验新版，排入已确认的自动维护流程；文件原件不回写。往返未发生源更新时数值不变，发生自动更新时须以新revision与对应源版本验证。只有系统文档流实际写入成功才报告成功，取消或写失败不改源数据。

## 证据与限制

本批检查 Schema 元结构、引用和正反结构样例；不实现或运行数据库事务、合并、迁移、目标状态、Android 文档访问与真实导出。未来 B03、B08、B09 需覆盖零上限、未知实际值、越界目标、重复键、超限、8/10有效记录、取消零写入、提交中失败回滚和导出往返。

设计采用 JSON Schema Draft 2020-12；格式检查必须显式启用，不能假定 `format` 自动成为断言。规范来源（2026-10-28核查）：<https://json-schema.org/draft/2020-12/json-schema-validation>。
