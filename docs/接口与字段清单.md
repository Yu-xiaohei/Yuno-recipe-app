# 接口与字段清单 v3

> 2026-10-28。新产品语义优先于旧 v2 清单；食谱 schemaVersion=2 保持兼容，新增配餐、目标和同步协议分别版本化。本文为待实现契约，不表示接口已存在。

> B01-candidate-7（2026-10-29）补齐：正式结构见 [schemas](../schemas/)，数量、仓储、目标及同步边界见 [契约评审入口](reviews/B01/README.md)。旧v2识别与canonical发布分开；以下清单与本批候选同步，尚待用户复核。

## 1. 单位、来源与精度

weight/carb/protein/fat/fiber 用 g；energy 用 kcal；vitaminC/sodium 用 mg。营养缺失使用 null，不可自动变成 0。weight 表示当前所列食材计量重量之和，不自动称为烹饪后出餐重量。

每项注明 foodState（如 raw/cooked/rehydrated）、营养取数口径和 sourceRef；每 100g 必须与 weight 的计量状态一致。缺失状态时标记待核实，不根据名字推断为已确认。

计算保留足够精度，展示时重量与 kcal 可保留 1 位，营养按适合的位数展示。从 per100 × weight / 100 重算，不反复缩放已舍入数字。合计显示值使用统一舍入策略；容差及修正项可追踪，不能静默篡改原数据。

## 2. Recipe（兼容 schemaVersion=2）

| 字段 | 规则 |
|---|---|
| schemaVersion / id / name | 正文版本、正文ID、名称；正文ID不是库唯一键，更名不自动更换ID |
| serving | 正数 number，允许 0.5；不能以 int 限制半份 |
| dishType / tags / summary / image | 分类、标签、摘要、可空图片 |
| revision / publishedAt；外部 contentHash | 正文保留版本和发布时间；原文件字节hash置于目录或传输元数据，不放回被hash的正文；与 generatedAt 区分 |
| includesStaple | bool 或 unknown，明确是否包含主食 |
| items[] | 食材明细，见下表 |
| totals / macroRatio | 派生缓存，导入与发布时校验，App 从明细重算 |
| targets | 兼容旧配方制作参考；不能当成用户全天目标 |
| notes / sources | 当前配方说明及来源引用 |
| generatedAt / generatedBy / user | 生成信息，不代替营养来源证明 |

食材：itemId、name、weight、foodState、category、per100、sourceRef、healthWeight、locked、可选 minWeight/maxWeight。per100 含 energy/carb/protein/fat/vitaminC/fiber/sodium，各值为非负数或 null。healthWeight 必须在 [0.01,1]，最多两位小数；locked 缺省 false。

原文件逐项营养值用于兼容与核验，不作为另一个独立事实源。源数据不一致时输出校验报告，由数据维护者确认；不凭空补营养、食材或权重。

库记录以(originNamespace,libraryEntryId)独立识别；必须核验SHA-256，不能按名称、正文ID或hash合并库记录。只有重复加入同一库记录才在配餐聚合xN；独立记录即使hash相同也分别显示、分别加入。稳定逻辑originNamespace不随OSS/GitHub/Gitee镜像切换；libraryEntryId在目录/本地元数据和配餐引用中，不注入被hash的正文。

## 3. GoalProfile 与 MealSlot

GoalProfile：id、revision、updatedAt、dailyGoals、mealSlots[]。

MealSlot：稳定 id、名称、顺序、enabled、allocationWeight、可选 mealGoals。重命名保持 ID；停用不删除历史记录。

每个 NutrientGoal：mode、unit、可选 target/lower/upper、warningFraction。mode 为 target、range、max；缺省未配置。单位必须与指标一致。

| mode | 绿色/达标 | 黄色 | 红色 |
|---|---|---|---|
| target | target>0 且相对差 ≤10% | >10% 且 ≤20% | >20% |
| range | lower≤actual≤upper | 离最近边界的距离 / max(upper-lower, (upper+lower)/2) ≤10% | 超过黄色范围 |
| max | 0≤actual≤upper | upper>0 且超出不超过 upper 的10% | 超过 upper 的110% |

range 需 0≤lower<upper；target 需 >0；max 允许 upper=0，此时 actual=0 达标，actual>0 超限，不做除零计算。无目标、实际未知均显示中性；目标无效拒绝保存。上述阈值是应用状态规则，不代表医学结论。

初版 warningFraction 默认 0.1；target 的红色边界固定为 0.2，后续变更须连同状态文案与测试更新。餐次按 allocationWeight / sum(weights) 分配日目标的对应边界；max 的分配仅是预算，不表示每餐必须吃满。手动覆盖明确标识并提示与日合计差额。

比例合计必须大于0，并验证每餐包含手动覆盖的最终目标；0权重导致非法0指定值或零宽区间时拒绝本次分配，保留原配置和编辑态。不能部分提交或静默改为未配置；合法max零上限仍可使用。详见[目标契约](contracts/goal-transfer-policy.md)。

## 4. MealRecord（个人配餐 schemaVersion=1）

| 字段 | 用途 |
|---|---|
| id / revision / parentRevision / deviceId | 稳定记录 ID、修订及同步比较 |
| date | YYYY-MM-DD，本地日历日期；不将零点 UTC 转换导致移日 |
| mealSlotSnapshot | 餐次 ID、名称、顺序 |
| goalSnapshot | 当时使用的目标、profile 版本、判定规则版本 |
| entries[] | RecipeSnapshot 或 IngredientSnapshot，含独立 entryId |
| totals / calculationVersion | 可复算合计、算法版本 |
| isLocked | 默认 false；显式解锁后可编辑 |
| syncEnabled | 此记录是否参与个人同步 |
| createdAt / updatedAt | 带时区时间戳；不能独立用于解决冲突 |
| deletedAt | mealRecord固定为null；删除使用独立kind=mealTombstone，携带身份、版本、日期/餐次及deletedAt |

RecipeSnapshot 包含originNamespace/libraryEntryId/sourceId/revision/外部字节hash、当前已应用版本的名称、源食材、调整后食材、目标总重量、调整结果、取数口径与来源。正式配餐每条总重至少1g；0≤重量<1g只允许保留无效草稿，不能导入或同步成有效记录。首版配餐调整和持久化仅使用mode=weight，与固定±100g滑块一致；不提供热量目标调整入口。独立食材使用相同的 per100 与 foodState 契约。公共食谱删除后历史仍可完整显示。

## 5. 调配计算契约

输入：原始食材快照、目标 mode=weight 或 energy、目标值 T、锁定及上下界、算法版本。
输出：新用量、新营养合计、requestedTarget、actualTarget、reachableMin/Max、status=exact/approximate/unreachable/invalid、warnings。

本节是纯计算端口的能力设计；energy保留为后续计算能力，不是首版配餐UI或已保存记录的模式。B03实现和用例应区分能力范围；未来开放energy入口前另行确认UX、快照格式及迁移，不能直接把该模式写入现有meal schema。

废止旧平均权重比例公式。建议首版采用以下确定性有界求解，并用实现测试验证：

1. 设原始克数 b_i>0，权重 w_i；重量目标 a_i=1，热量目标 a_i=per100.energy/100。
2. 增量偏好 p_i=w_i；减量偏好 p_i=1.01-w_i。locked 固定 g_i=b_i。
3. 未指定食材边界时使用工程保护范围 0≤g_i≤2b_i；这不是营养建议，可由配方提供更合适的 minWeight/maxWeight。增量不减其他项、减量不增其他项。
4. 在边界内最小化 Σ[((g_i-b_i)/b_i)^2/p_i]，约束 Σa_i g_i=T。可用单调乘子 g_i=clip(b_i+λ p_i b_i² a_i,lower_i,upper_i) 和二分求 λ。能量系数为 0 的项在热量目标下保持不变。
5. 先计算可达区间；不可达时求最近可达边界并明确标记，不输出“已达目标”。所需能量未知则禁用热量求解；重量求解可继续，但营养合计标记不完整。
6. 未舍入结果残差应 ≤0.01g 或 ≤0.01kcal；呈现及可执行用量量化后允许 ≤0.5g / ≤0.5kcal，超过则 approximate 并展示偏差。量化不得破坏 locked 或边界。

高权重是分配偏好，不承诺每种食材的变化量严格按权重排序。每次从原始快照计算，保存实际变化并可重置。删除条目是独立操作，不将全零结果存成有效食谱。

## 6. 公共源与更新

version.json：协议版本、recipes manifest 版本、app versionCode/versionName、apk 路径、hash、更新说明。recipes manifest：libraryEntryId、正文id、revision/hash、相对文件路径及与已验证全文一致的摘要。

公共食谱和图片使用 OSS 的已发布公共 HTTPS 资源，GitHub/Gitee 可提供同构数据镜像并分发 APK；私人配餐不上传这些公共源。各源结构一致，客户端优选与失败回退；路径相对当前可用源解析，避免切源后仍指向失败的绝对域名。时间较近不等同内容完整；只有验证通过的记录提交。具体公开地址与镜像可用性按部署校验，不在 APK 放发布凭据。

状态：idle/checking/downloading/partial/success/offline/error。记录 manifest 版本和各条目 appliedRevision；部分失败须可重试。公共库当前正文直接替换且不保留旧版列表；已保存配餐及活动草稿中的对应Recipe自动替换并重算，保留目标/餐次/份数/锁定，生成新revision并按已配置同步入队；按D13保留已接受实际总重；越界按已确认D14自动调整至新版有效上下限。应用更新 versionCode 用整数比较；不通过字符串版本比较强制阻断离线数据。

## 7. 导入、导出与本地接口

首版普通用户仅支持`mealBackup`配餐备份导入导出；`libraryImport`食谱/食材导入仅开发者模式测试，导入后暂不可删除。入口、文件kind分派、深链、预览与提交均检查开发者能力。备份中的内嵌快照仅恢复配餐，不创建库记录。

配餐正式记录及草稿条目增加可选`sourceAvailability`，已有可信下架事实时保存`status=withdrawn/catalogRevision/deletionRevision/deletedAt/observedAt`。字段缺省只表示未确认下架；条目本身的sourceRevision/hash仍指最后保留配方。证据随同步/备份传递，不能冒充私人tombstone，详情顶部据此提醒。来源维护及上下限规则见[数量契约](contracts/quantity-policy.md)，餐次预设及Figma节点见[目标契约](contracts/goal-transfer-policy.md)。

导出 envelope：schemaVersion、kind=mealBackup、exportedAt、records[]、可选 goalProfiles。排除密码、token、设备私钥及日志。导入先识别 kind/schema，预览数量、日期、重复 ID、无效数据和冲突；无效记录逐条列原因，确认后只提交有效记录，10条中2条错误时导入8条；取消不改本地，任一提交失败回滚。未知高版本明确拒绝，不静默丢字段。

本地边界：RecipeRepository（公共及导入库）、MealRepository（记录与事务）、GoalRepository、SettingsRepository、SyncRepository（队列、基线与冲突）。具体数据库在工程阶段选定；不要把所有配餐塞入设置键值存储。

## 8. WebDAV 协议与冲突

远端个人目录与公共食谱目录隔离。记录以稳定 ID 存储，带 revision、parentRevision 和内容 hash。同步元信息记录 lastSyncedRevision/ETag。

首版优先联调 123 云盘 WebDAV；官网提供协议支持不代表账号权限及条件写入已经通过测试。OSS 仅用于公共资源，不作为本协议的私人配餐同步后端。详见《存储与分发接入基线.md》。

经能力探测确认强ETag及条件写入可靠后，使用 If-Match/If-None-Match 条件写入；弱ETag不提供强比较保护，读取失败不解释为远端不存在。双方都改动基线的同一记录时建立 conflict 副本，保留原 ID 关联和双方版本，供用户选择完整候选；不逐字段盲合并。服务不支持可靠条件写入时停用无人值守覆盖，提供显式备份及恢复流程。

不同ID也须检查同日期+稳定餐次ID唯一；占用相同槽位时进入独立冲突存储，不插入第二份有效配餐。删除标记参与同步，不能直接丢弃导致复活。清配餐本地数据按选项2同步删除远端配餐，可靠列举、预览和确认后持久化tombstone/outbox；离线保留待处理，不声称云端已清空。食谱删除只能从云端发起，本地跟随显式删除，历史快照保留。用户解决冲突生成新revision，条件提交并回读验证成功后才标记对应冲突已处理；失败保留副本。设备时钟只用于展示，不决定胜负。详见[同步契约](contracts/sync-policy.md)。

凭据安全存储、网络日志脱敏；锁定记录仍可同步、导出与主动解锁。同步状态包含 disabled/pending/syncing/synced/failed/conflict，并能说明是否只是本地保存成功。
