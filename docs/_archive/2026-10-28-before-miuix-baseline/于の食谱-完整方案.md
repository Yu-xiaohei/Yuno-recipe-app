## 1. 产品与首版范围

面向公众发布的 Android 食谱浏览与配餐工具。用户浏览结构化食谱，按日期和自定义餐次搭配食物，调整配方用量，对照自己设置的营养目标，并可导出或备份个人配餐。

由 AI Agent 完成设计、开发和自动验证；App 首版不内置 AI 对话、模型调用或 AI 营养规划。配餐“生成”指确定性计算与保存，不暗示模型自动推荐。

首版包含：
- 食谱首页、独立搜索、筛选、食谱详情与离线浏览。
- 日期配餐、自定义餐次、按 healthWeight 调整食材、配餐锁定与解锁。
- 用户自定义营养目标、目标区间与仅上限判定。
- 食谱及配餐 JSON 导入、配餐 JSON 导出、个人 WebDAV 同步。
- 食谱库更新、应用更新、主题、省流、缓存管理与隐藏开发者模式。

首版不包含社交、打卡、自动医疗或营养处方、多平台客户端。正式图标、发布渠道及签名交付仍需发布阶段确认。

## 2. 资料优先级

本次已确认的决定 > 本版跨文档规则 > 当前 Figma 与 UX > 归档旧方案。Figma 的演示数字不构成默认推荐目标；冲突处按本文及接口计算规则修正。

导航固定为“配餐 / 食谱 / 设置”，默认进入中间的食谱首页。搜索是子页，不是第四个 Tab。任何日期均可打开；没有配餐时显示空餐次并允许新建。搜索至少 2 个有效字符。

## 3. 用户数据与公共数据

| 数据 | 来源和归属 | 修改与更新 |
|---|---|---|
| 公共食谱 | 发布的食谱数据源；内置样例兜底 | 客户端只读更新；个人配餐不回写公共源 |
| 本地导入食谱 | 用户选择的 JSON | 校验后加入个人食谱库；同 ID 冲突必须明确处理 |
| 配餐 | 日期 + 餐次 + 食谱/食材快照 | 本地保存优先，可导入导出及 WebDAV 同步 |
| 营养目标与餐次模板 | 用户设置 | 新配餐使用当前模板；历史使用保存时快照 |
| WebDAV 凭据 | 用户个人服务器配置 | 使用平台安全存储方案，不进入配餐导出及日志 |

公开食谱同步与个人 WebDAV 是两条独立链路，设置和错误提示须分别展示。无需向聊天提交仓库 token；后续发布采用本地凭据或服务授权。公共只读源是首版部署选择，不把“私有仓库必须在 APK 中放 token”作为技术结论。

## 4. 食谱与配餐的边界

食谱是标准配方；配餐是一餐中多个配方或独立食材的组合。食谱名、食材状态、营养数据与说明必须匹配。已剔除米饭的“时蔬饭”应明确标为不含主食的配菜，避免用户误以为已计入米饭。

保存配餐时保存原食谱版本、原始配方、调整后的食材用量与营养、日期、餐次名称、目标快照、修改信息及同步标识。以后公共食谱更新、用户改目标或改餐次名称，都不自动重算历史。

编辑旧配餐默认沿用原快照。更新到最新版食谱或当前目标需要显式操作与预览。锁定仅限制编辑，用户可主动解锁；删除仍需确认。

## 5. 目标与状态

目标完全由用户设置，未设置时不显示达标结论。设计稿中的 1000 kcal、钠数值等仅作排版演示，不作为面向所有用户的预设。

支持：指定值及容差、目标区间、仅上限。钠等指标可选择仅上限，低于上限不提示“缺少”。具体判定公式、未配置和零目标处理见接口文档。颜色同时搭配文字或图标，不单靠红黄绿表达状态。

日目标可按餐次比例分配；用户手动修改某餐后显示手动状态，禁止后台静默覆盖。各餐合计与日目标不一致时提供差额和“按比例重分配”操作，不伪装为一致。

## 6. healthWeight 与重量调整

用户确认：配餐拖动重量始终按 healthWeight 重新分配食材，允许配方比例变化。该字段保留兼容名称，产品文案称“调配优先级”，不宣称其为经过验证的健康评分。

优先级由食谱数据提供，App 不通过名称自动推断并当作事实写入。增量优先分配给较高值食材；减量优先调整较低值食材。locked 项保持原克数；达到边界后重新分配剩余量。

旧版按平均权重乘比例的公式废止：它不能保证满足总重量或热量。采用有边界的约束求解，见接口文档。不可达时显示可达范围与实际值，用户决定应用或取消。

±100g 保留为默认微调入口，并受可达范围约束；另提供直接输入，不能仅靠滑块输入。始终从原始快照重算，禁止反复对舍入后的结果累乘。

## 7. 搜索、筛选与详情

搜索有效字符至少 2 个，忽略首尾空白；输入法组合文字未提交时不搜索。支持菜名、食材名、中文跨字匹配、全拼与首字母；按完整名称、连续命中、跨字及拼音匹配的相关度排序。同一筛选维度多选为 OR，不同维度及搜索之间为 AND。

默认食谱按发布时间倒序；不要把本地导入或最近修改的时间冒充原始生成时间。无图片使用现有碗与叶子占位。

详情突出名称、是否含主食、热量、重量和营养；来源、每 100g 口径、生成信息可展开。手机明细使用食材行与展开内容，完整宽表作为可选详细视图。公共食谱不提供与配餐重复的调配入口；首版在配餐中统一调整。

## 8. 离线、更新与同步

启动先展示本地可用数据，后台检查食谱更新；网络不作为进入应用的前置条件。有旧数据时保留内容，仅显示同步状态；首次无可用数据才使用骨架或错误页。

食谱下载先暂存、校验再提交；只有全文校验通过的条目才能更新索引摘要。失败保留旧版本并标记部分失败。逐项版本/hash 与库版本分别记录，避免“库版本最新”掩盖未完成条目。

WebDAV 默认先保存本地，再排队同步。离线、失败、待同步、成功、冲突分别显示。用同步基线与条件写入识别冲突；同一配餐双端修改保留双方副本，由用户处理，禁止仅按设备时钟覆盖。删除采用 tombstone，防止另一设备恢复旧记录。

应用更新由用户触发安装；须验证下载文件完整性及签名兼容性。首版不因远端版本字段阻断离线浏览。更新源故障不能连带阻断个人配餐。

## 9. 视觉与工程边界

保留当前蓝色强调、浅底白卡、碗叶占位、胶囊导航及液态玻璃方向。Figma 是布局、层级与状态参考，真实背景采样、折射及动态效果必须在 Android 原型和真机验收。

Android/Kotlin/Compose 为当前候选主线，沿用包名 com.yunobase.recipe。最低系统、target SDK、组件库版本、玻璃性能与分发合规要求在工程启动时核实；旧稿关于特定库模块和“完整可行”的描述不作为已验证结论。

## 10. AI Agent 交付方式

每阶段交付文件、变更摘要、自动验证证据和未验证项。自动化承担数据一致性、目标求解、历史快照、导入和同步协议测试；用户承担风格反馈、必要的账号授权及真实设备体验确认。无需把每个小任务都设为人工批准关卡。

阶段按“规则与数据 → 核心闭环 → 目标和调配 → 同步与恢复 → 视觉动效 → 发布验证”推进，详细验收见任务清单。当前本轮交付为文档统一与设计稿语义修正，不表示 Android App 已开发完成。
