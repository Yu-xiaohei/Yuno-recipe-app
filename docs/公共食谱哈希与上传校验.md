# 公共食谱哈希与上传校验

状态：B01补充工具，可本地执行；尚未推送运行GitHub Actions，也未部署OSS或实现Android下载器。现有13份`data/reference`旧数据不参与正式发布。

## 已建立的方法

每个Recipe/Ingredient正文文件按原始字节计算`SHA-256`，输出64位小写十六进制，写入独立的`catalog.json`条目`contentHash`。正文不嵌入自己的hash。空格、BOM、LF/CRLF和末尾换行均参与计算；不得先解析、格式化或重写正文后再核验下载文件。

库身份仍是`(originNamespace, libraryEntryId)`。同名、同正文ID、同hash、甚至共用同一路径的不同库记录均独立保留；hash不负责去重。Git提交ID、Git blob ID及HTTP ETag均不能代替`contentHash`。SHA-256证明字节一致，来源可信还依赖已配置的HTTPS源及发布权限。

工具为[scripts/catalog_integrity.py](../scripts/catalog_integrity.py)。仅使用现有固定检查依赖；JSON严格拒绝重复键、NaN/Infinity，十进制数不经float重新舍入，Schema离线解析。读取正文的一份原始字节同时用于hash及结构检查。

## 维护与生成

1. 将已按canonical规范准备好的正文放入`data/public/`，使用安全ASCII相对路径，例如`recipes/example.json`。保留`data/reference/`原件。来源、许可、计量状态和营养算法仍需对应审核。
2. 在[config/catalog-publication.json](../config/catalog-publication.json)登记`operation/libraryEntryId/kind/path`。工具从正文推导`id/revision/summary`，无需手填hash；新库记录需要新的稳定内部ID，不能用hash当ID。
3. 修改同一条食谱的字节时，更换正文`revision`及目录计划`revision`，填写本次`generatedAt`。目录或摘要变化也必须更新目录revision。显式删除使用`operation/libraryEntryId/kind/id/revision/deletedAt`，保留删除标记；从计划缺席不是删除。
4. 运行生成与独立核验，再检查差异。生成先完整检查全部输入，成功才原子替换目录；失败保持原目录和正文。核验只读，不回填hash、不修复源文件。

```powershell
.venv/Scripts/python.exe scripts/catalog_integrity.py build --baseline-ref HEAD
.venv/Scripts/python.exe scripts/catalog_integrity.py verify --baseline-ref HEAD
git diff -- data/public config/catalog-publication.json
```

当前计划和目录为空的`bootstrap-1`，只用于验证工具链；不代表已有正式食谱，更不能覆盖线上已有目录。已知上一版的库记录不可直接消失，删除必须显式登记。首次建立目录时，Git基线没有目录可供比较，需要正常人工审阅新目录。

## 提交前后核验

暂存经过审阅的计划、正文、引用图片和目录后执行：

```powershell
.venv/Scripts/python.exe scripts/catalog_integrity.py verify --git-mode staged --baseline-ref HEAD
```

这一步检查将提交的Git blob与刚才校验的工作树原字节逐一相同，覆盖计划、目录、正文和引用图片；拒绝未跟踪、未合并、符号链接及暂存旧字节。`.gitattributes`对公共目录及计划关闭换行、filter、ident和编码转换。工具批量读取Git对象，不逐个启动数千次进程。

提交后，在该提交的干净检出中执行：

```powershell
python scripts/catalog_integrity.py verify --git-mode head --baseline-ref HEAD^
```

[GitHub工作流](../.github/workflows/catalog-integrity.yml)在推送`main`、向`main`提PR及手动触发时，于Linux/Windows执行固定依赖测试和HEAD字节核验；权限仅`contents: read`，不自动提交、推送或发布。PR比较base SHA，main推送比较before SHA；首次main无before时比较父提交，真正根提交没有旧目录。功能分支通过PR验证，避免把新分支的全零before当作旧发布目录。

Gitee使用同一套命令。两个远端推送后，回读各自`refs/heads/main`应等于本次本地commit，再在独立检出中核验；远端发生分叉时停止，不强推。Gitee CI和GitHub必需状态检查/分支保护尚未配置，不能声称检查失败已能阻止所有直接推送。

## 正式上线与应用端交接

未来发布按“正文及图片先上传→回读核验→最后切换目录”执行；镜像用同一套已审阅字节，不在服务器重新格式化。运行中的App先暂存下载字节，核验hash，再解析并校验kind/id/revision/摘要及业务语义，全部通过后事务替换；失败保留当前有效内容，不自动覆盖私人配餐。来源更新和下架仍遵循[数据契约](contracts/catalog-data.md)与[数量契约](contracts/quantity-policy.md)。

下载后hash失败：丢弃本次暂存、保留当前有效条目并报告失败；不能重新计算一个hash写回目录来让它通过。目录和正文必须来自同一个已确定发布版本；OSS缓存/目录切换及源HTTPS白名单在B10实现和测试。图片当前只做存在性及Git上传字节检查，尚无App图片独立hash契约。

本工具不证明营养总和、边界求解、来源事实、素材许可或签名真实性。每输入文件及生成目录上限16MiB、输入合计256MiB、目录最多10000条是工具资源保护，调整需重新评审与测试。B03生产语义、B10实际下载/OSS、Android运行和云端CI仍未验证。

## 失败与恢复

build失败时原目录不变；核验失败先修正文、计划或暂存差异，再重新审阅。已公开的错误提交用新的修正提交恢复，重新生成及核验后再同步两个远端；不默认force push、不删除远端历史。实际推送、线上目录切换或删除仍遵守项目双次确认规则。

资料核对：Python 3.14 `hashlib`，Git `gitattributes`/`cat-file`/`hash-object`，GitHub Actions安全使用参考；检查于2026-10-30。Action固定提交已通过官方仓库`ls-remote`核实，具体版本见工作流注释。
