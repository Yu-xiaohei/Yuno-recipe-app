# 食谱数据生成技能改造说明 v3

> 2026-10-28。本文是后续 recipe-nutrition 技能的改造契约，不是要求本轮立即修改或运行该技能。现有原始 JSON/Markdown 暂不批量迁移。

## 1. 输出目标

生成可追溯、可计算、字段一致的食谱数据。App 首版不调用 AI；AI Agent 在制作食谱与软件时使用技能。生成模型的名称不等同营养数值来源。

食谱兼容 schemaVersion=2，字段及精度以《接口与字段清单》为准。不能仅因 schema=2 就判定所有新字段和营养口径已完备。

## 2. healthWeight 与 locked

每项 healthWeight 在 [0.01,1]，最多两位小数，用作调配偏好。较高值在增量时更受优先、减量时更受保护；这不是经验证的健康评分，不对公众承诺“越高一定越健康”。

按该食材在此配方中的角色给出理由；不要无条件套类别表。缺失权重的旧数据输出待审清单，在补齐前禁用权重调配，仍可浏览。

locked 默认 false，仅在配方或用户明确要求固定克数时设 true。废止“所有盐/糖/味精一律锁定”的要求；低权重与锁定是不同语义，不应同时要求减量优先削减又禁止调整。

可选 minWeight/maxWeight 用于配方边界，须包含原始克数。不能把算法的保护边界说成营养学建议。

## 3. 营养与生熟口径

每项保存食材状态、每100g数据和来源引用。干粉丝与泡发粉丝、熟米饭与生米不能共用重量口径；若换算需保存换算依据及原始值，无法核实则标记未知。

单位固定：纤维和三大营养为g，钠和维生素C为mg，能量为kcal。表头“维生素”明确写“维生素C”。缺失数据为null，不能作为0参与“完整营养”结论。

每项营养从per100与重量计算；totals从食材明细计算；macroRatio从统一计算规则得出并记录版本。考虑原始数据舍入与缺失，不强行让供能估算等于来源总能量。

## 4. 名称、范围与说明

剔除主食后，名称、summary、includesStaple、notes与来源列表一起审核。可以保留原名作为别名，但界面明确“不含米饭/面条”。来源列表不得让用户误以为已剔除的主食仍计入总量。

notes应描述当前食材与数值。调整后旧文字中的热量、重量、达标结论不能直接照搬；动态结论由App基于快照计算，原始备注保留为来源说明。

## 5. 校验与交付

校验器负责结构、范围、单位、引用关系、合计与口径一致性；AI负责给出可复核理由，不能用校验通过证明营养数据来源可靠。

交付包含原始文件、建议文件、逐字段diff及问题清单。不得无报告覆盖存量文件。迁移只补可确定字段；未核实的权重、营养来源、生熟转换不可静默编造。

当前样例“香菇木耳时蔬饭”的各项明细合计与totals一致，但名称含饭而notes表示不含米饭，且粉丝干湿口径及来源映射仍需核实。该样例本轮不擅自改营养数值。

## 6. 技能验收

- 新生成食谱字段齐全，权重与锁定理由可复核。
- 无效/缺失数据能报错或明确降级，不当成正常数据。
- 重新计算不改变原始文件；输出差异与舍入解释。
- 不含主食的配方在名称/说明/UI中一致。
- 与App的约束求解器使用同一字段契约，不在技能里另外发明一套缩放公式。
