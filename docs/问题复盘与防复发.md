### ISSUE-20261028-01：Windows PowerShell 与 Python 混用时的中文编码误判

- 现象：通过 PowerShell 管道向 Python 传递中文脚本或直接查看输出时出现乱码；控制台乱码一度被误判为文件内容损坏。
- 根因：PowerShell 管道编码、控制台代码页和 Python 输入编码不一致；带空格或中文的路径也会增加误判机会。
- 修复：文件写入统一使用 UTF-8；需要从 PowerShell 传给 Python 的中文文本改用 ASCII `\\uXXXX` 转义；读取时用 Python 按 UTF-8 解析并检查替换字符和控制字符。
- 防复发：中文文件优先用 `apply_patch` 或 UTF-8 明确写入；PowerShell 路径使用 `-LiteralPath`，命令行路径始终加引号；不能根据控制台字形判断文件是否损坏。
- 验证：JSON 可解析，UTF-8 替换字符扫描通过，Markdown 链接和代码围栏检查通过。
- 2026-10-29关联复现：Python控制台输出中文失真但文件UTF-8正常；仅为当前进程设置`PYTHONIOENCODING=utf-8`后可读。PowerShell中含空格路径必须整体加引号，不能使用Bash的反斜线转义空格；错误的只读检索已按实际引号路径重跑，未据此判断文件不存在。
- 同日收尾补充：`PYTHONIOENCODING`不控制`subprocess.run(text=True)`的解码；Git含中文路径的UTF-8警告被系统GBK读取线程误解码。改用字节模式捕获Git输出并核验退出码，文本需要时再显式UTF-8解码；文件内容及Git检查本身未失败。不能忽略后台读取异常就把该轮验证器视为完整通过。

### ISSUE-20261028-02：一次性长脚本在中途失败，造成部分文件已写入

- 现象：批量更新脚本先写入机器契约和计划文件，随后因旧版 UX 文稿不存在预期行而停止；如果直接报告整体完成，会留下跨文件不一致。
- 根因：写入前没有对所有定位点做唯一命中预检；脚本把多个相互依赖的写操作放在同一段流程中，且没有事务式提交。
- 修复：保留已成功写入的文件，按实际段落重新定位并补齐剩余文件；随后重新执行 JSON、ID、依赖、链接、UTF-8 和语义一致性检查。
- 防复发：批量修改先做只读预检，所有定位点必须唯一命中；复杂变更优先使用小批次 `apply_patch` 或先写入带 `tmp_` 前缀的中间文件，全部检查通过后再替换；脚本必须可重复执行且不会重复追加内容。
- 验证：最终检查通过，候选为 `B00-candidate-8`，15 批次、85 任务、30 页面、152 状态、74 验收场景，依赖无环。
- 2026-10-29关联复现（2026-10-30补记）：候选3批量写入已做全部文本/JSON预检，但相对路径写`docs/UI设计稿需求.md`仍遇到`OSError: [Errno 22] Invalid argument`而中断，前序配置已写入。立即回读实际文件、字节和已命中变更，失败目标原文完整；该单文件用apply_patch完成，剩余改为解析后的绝对路径、可重入替换、逐文件写入后立即回读，全部补齐并通过跨文件检查。底层Errno22触发因素未确定，不能把绝对路径重试成功当成已查明环境根因；已修复的是部分更新的一致性及恢复流程。预检不能消除运行时写失败，后续仍要明确已写清单、停止点及最终整体复检。

### ISSUE-20261028-05：本地 Git 提交被 `.git` 写权限阻止

- 现象：暂存完成后执行中文初始提交，Git 无法创建 `.git/index.lock`，返回 `Permission denied`。
- 根因：当前受限执行环境允许修改项目工作树，但对项目 `.git` 元数据目录默认只读；不是仓库内容或锁文件残留问题。
- 修复：先确认不存在残留 `index.lock`，再使用受限的权限提升重试同一条本地提交命令；没有修改提交内容，也没有绕过 Git 锁机制。
- 防复发：初始化或提交前检查 `.git` 元数据写权限；遇到锁文件错误先检查锁文件归属和进程，再决定是否使用最小范围的权限提升；不直接删除未知锁文件。
- 验证：提交 `07c6a5b` 成功，工作区干净，远端回读与本地提交一致。
- 影响的文件/批次：本地 Git 初始化与首个提交；不影响 UX、数据契约或 P0 计划。
- 未验证项或限制：权限提升依赖当前执行环境，其他 Agent 或机器仍需单独检查 Git 元数据写权限。
