# 页面与组件契约

> 2026-10-28，开发交接源稿。这里的页面用途名和线框注释不直接成为 App 新文案。新用户可见名称须用户确认；“食材”标签已确认。逻辑路由和组件角色尚未实现，不是 Miuix API 声明。

## 1. Agent 如何使用本契约

先从 [流程与状态](流程与状态.md) 选择流程，再从 [screen-contracts.json](screen-contracts.json) 读取对应页面。每页都提供 `route / inputs / states / actions / dataInterfaces / componentRoles / acceptanceCases / pendingDecisionIds`；内部事件名可按工程规范映射，不能只实现成功画面而略去取消、失败与副作用。

`route.pattern` 是逻辑导航契约，不要求采用特定 Navigation 库或把参数原样放进 URL。`draftId`、`mealId` 传引用，不在路由携带完整配餐、凭据或隐私内容。`RETURN` 恢复来源上下文，`SYSTEM` 进入系统文档选择器/安装器。配置、历史和计算结果的权威字段以 [接口与字段](../接口与字段清单.md) 为准；本契约只补交互边界。

`ST-Sxx-key` 仅是页面局部状态标识，不自动成为数据库枚举；`AC-Sxx-nn` 是待执行验收场景。D 标记用来阻止未经确认的默认决定，默认逐项问用户，用户要求时可合并问题。D01/D02/D03/D04主体/D05/D06/D07/D08/D09/D11 已获用户确认，保留 ID 作为决定引用；D10 与 D12 仍保留工程核验或 schema 设计范围。候选动作的 D 引用不阻塞独立已确认流程。

## 3. 结构线框与组合方式

线框只规定阅读顺序和操作关系，不固定尺寸、最终字符串、字重数值或材质参数。底部保持三个全局 Tab；库内类别标签与全局导航使用不同层级。宽度不足和大字体时改为换行/纵向，不能缩到不可读。

```text
S02 食谱；S27仅复用库内类别与列表骨架
┌─────────────────────────────────┐
│ 页面标题          搜索   筛选    │
│ 库内类别：食谱 | 食材             │
│ 已应用筛选 / 更新状态（有则显示） │
├─────────────────────────────────┤
│ 图片 + 名称                      │
│ 重量/热量 + 完整性/来源状态       │
│ 分类信息                 详情入口 │
│ ……列表；内容先于装饰              │
├─────────────────────────────────┤
│ 配餐         食谱         设置   │
└─────────────────────────────────┘

S09 配餐编辑
┌─────────────────────────────────┐
│ 返回    配餐编辑        保存意图  │
│ 日期 / 星期 / 餐次：只读上下文    │
│ 目标与实际：文字值 + 语义状态     │
├─────────────────────────────────┤
│ 食谱/食材  名称、xN、总重/总热量  │
│ 调整入口 / 减一份操作             │
│ ……条目；缺营养显示未知/不完整     │
│ 添加食谱/食材入口                 │
├─────────────────────────────────┤
│ 本地保存状态 / 可选同步状态分开   │
│ 主要保存操作；键盘上方可达         │
└─────────────────────────────────┘
```

食谱卡片承担“浏览摘要”，配餐条目卡承担“已选快照+调整”，不能因外观近似就共用不同业务状态。S02默认发布时间倒序，卡片显示图片/碗叶占位、名称、总重/热量和2–3分类标签。食材标签共用列表壳体；这里未扩展承诺食材专属搜索/筛选。食材详细信息从用户单独发布的每 100g JSON 读取，不从食谱的同名食材抽取营养，不提供首版 App 内手工营养录入。

S05 详情先展示标题、图片和计量口径，再展示营养、食材与来源，最后为加入意图；展开食材不改变公共配方。S11 食材详情明确每 100g 定义及加入重量，缺字段不补 0。加入路径总能回到来源位置，不能丢当前搜索、筛选、滚动或草稿。

S14/S15 先选日/餐范围和指标，再选目标类型并显示对应字段：`target` 只显示目标值，`range` 显示上下界，`max` 显示上限。类型切换后隐藏字段不应意外参与校验；取消保留原目标。表格/列表必须同时有值、单位和状态语义，不能只靠颜色。

S21 导入先展示种类/版本、范围/数量、无效项与重复/冲突，再展示确认提交；确认按钮在校验或未完成冲突选择时不可执行。S20 冲突对比按日期、餐次、条目、目标、版本展示双方差异，先选处理方式再确认；取消保留双方副本。比较表大字体下逐项上下排列，避免横向缩字。

## 4. 核心交互与副作用契约

| 边界 | 可见行为 | 写入 / 不变量 |
|---|---|---|
| 启动与空库 | 默认进入食谱；空库/错误可操作，有重试且保留导航 | 不等网络成功；不静默初始化推荐营养目标 |
| 搜索与 IME | 未提交组合输入不查；提交且去空白后至少2有效字符才查询 | 有效提交后才写去重历史；应用不设条数上限，UI 最多显示5行，超出由设备策略清理 |
| 筛选 | Figma 热量/重量/分类弹出选项按已确认边界；同维度OR、不同维度及搜索AND | 取消不提交；无结果提供清筛选入口 |
| 日期餐次 | 日历无餐日期同样可选；编辑页上下文只读 | 日期为本地日历日期；同日期+餐次仅一份，继续添加编辑已有 |
| 重复条目 | 相同定义显示xN与聚合重量/热量；微调作用总量一次 | 保留原始单份与份数，减份扣原始单份并重算；负值归零；0–9g红框无效、可用滑块修正且不可保存；D12身份及原始份量契约复核前不实施猜测 |
| 调配预览 | 显示请求值、实际值、可达范围与食材差异 | 从原始快照有界重算；锁定食材克数不变；不可达需明确应用实际值 |
| 配餐保存 | 本地成功后才转详情；失败留草稿；无目标或部分营养未知有相应提示 | 至少一个条目且所有条目重量至少10g、字段有效才可本地保存；存在0–9g时定位红框并阻止提交；同步晚于本地事务，不回滚已成功本地数据 |
| 离开编辑 | 顶部/系统返回/跨Tab统一保护草稿 | 继续编辑、保存后离开、明确放弃分开；保存失败不得离开并丢草稿 |
| 配餐锁定 | 用户显式锁定/解锁，锁定后仍能查看、同步与导出 | 锁定变更事务成功后才成为最终状态；加入锁定配餐先显式解锁 |
| 历史快照 | 显示当时配方、食材、目标、营养与餐次名称 | 公共更新、模板改名和目标变更不自动重算历史 |
| 导入 | 预览后确认；无效记录逐条列出原因，确认后只导入有效记录；未知高版本明确拒绝 | 提交前零写入；提交失败回滚；10条中2条错误时只导入8条 |
| WebDAV | 本地保存、排队、同步成功、失败和冲突含义分开 | 不用设备时间决定胜负；双方变化保留冲突副本；无可靠条件写入降为显式备份/恢复 |
| 公共更新 | OSS公共数据只读；失败保留有效缓存，部分失败能重试 | 校验全文/摘要/版本/hash后事务提交；不上传私人配餐 |
| APK更新 | 用户主动检查、下载和安装，可取消 | 校验完整性及签名兼容；系统安装器返回后读取实际版本 |
| 清理 | 图片缓存与全部本地数据明确分类；配餐按选项2与远端一并删除；食谱只能云端删除并同步移除 | 清缓存不删配餐；两类数据均显示同步结果与失败重试 |

重复例已确认：`原始300g × 2 = 600g → 固定滑块500~700g → 微调+100g = 700g → 删除一份扣原始300g → 400g × 1`。不按当前平均份量350g扣减，不把700g再乘2。P0需为份数、原始单份、聚合目标与快照定义一致的数据和计算契约；重量滑块以原始单份×当前份数为锚点，仅±100g，不连续累加；份数改变后按剩余份数对应的原始叠加量计算固定范围。删除导致负值强制归零；0–9g保留为红框无效状态，可通过滑块修正，保存时定位并阻止提交，所有条目调整到至少10g后才满足重量有效条件；不能自动改成10g或移除。首版不提供直接输入；D12仅保留identity与独立食材原始份量来源等契约设计，不自行clamp/平均或把每100g营养口径等同原始单份。

独立食材属于库中独立 Ingredient 定义，加入配餐后是 IngredientSnapshot；RecipeSnapshot 内的食材仍属于当时配方。两者不能因名称相同就互相替换。公共 Recipe 来源以 100g 起步；Ingredient 的每100g是独立营养口径，不自动等于加入时原始单份或配餐最低重量；份量来源在P0与schema一并冻结。Ingredient JSON 具体 schema、目录/manifest 扩展在 P0 设计并复核，本轮不虚构正式字段格式。

## 5. Miuix 角色映射

[screen-contracts.json](screen-contracts.json) 中 `componentRoles` 定义逻辑角色，`upstreamApi=null`、`apiStatus=version-mapping-required` 是刻意的边界。工程 Agent 依固定版本的官方源码/演示确认真实名称与参数，不能按角色名编造组件 API。

| 角色组 | 页面用途 | 组合约束 |
|---|---|---|
| app_shell / modal_surface / more_menu | 全局壳体、筛选、上下文选择、更多操作 | 遵循 Miuix 导航/弹层/动效；返回层级明确；遮罩关闭不丢草稿 |
| recipe_card / entry_card / ingredient_row | 公共摘要、配餐快照、食材明细 | 按业务角色区分状态；名称可换行；重量/热量是有单位的总量 |
| search_input / form_input / choice_control / toggle_control | 搜索、目标、日期餐次和设置输入 | IME组合态、安全键盘、错误与可编辑状态清晰；数值不合法不强制改成0 |
| nutrition_summary / nutrition_table / status_feedback | 目标、实际、缺失、达标与超限 | 语义色加文字/图形；未知/无目标为中性；不得使用玻璃导致对比不足 |
| weight_control / ingredient_diff | 请求调配、可达值和用量差异 | 预览与提交分开；保留锁定项；减份不等于整体删除 |
| settings_group / settings_row / day_summary / meal_slot_card | 设置分组、日摘要、餐次入口 | 统一层级与字体；停用模板不隐藏旧记录 |
| primary_action / sticky_action / confirm_dialog | 主要提交、危险确认和退出保护 | 滚动/键盘/大字体下可达；不可执行时说明原因，不能只降低透明度 |
| comparison_panel / import_summary / release_summary / progress_feedback | 差异、导入、版本和进度 | 有取消/失败/重试路径；进度完成不能替代实际结果复核 |

API31/32使用清晰的简化玻璃表面并保留 Miuix 动效；API33+增强材质按兼容性原型结果启用。材质选型不改变布局可读性、业务结果或保存能力。一个APK优先，安装与低版本启动测试未通过时按已确认备用方案处理，不能仅靠运行时if声称兼容。

## 6. 通用状态与可访问性

| 状态 / 场景 | 必须可审阅的结果 |
|---|---|
| loading / refreshing | 首载占位与已有内容刷新区分；刷新失败保留现有内容 |
| empty / no_result / empty_day | 说明当前无内容的原因，提供相关入口；不自动强迫联网或生成数据 |
| error / offline / partial | 错误可重试、可返回；离线内容可读；部分失败明确影响范围 |
| saving / failed / synced | 禁止重复提交；本地失败留草稿；同步结果另行展示 |
| 目标未知 / 数据缺失 | null与0不同；实际不完整标记；无目标保持中性 |
| dark / light | 语义层级一致，图标与正文对比可读；错误/选中/禁用可区分 |
| 大字体 / 长中文 / 多行卡片 | 控件随内容增长，主要操作不被裁切；关键营养值不以省略号代替 |
| IME / 键盘 / 安全区 | 关键字段和提交不被键盘或导航栏挡住；组合输入不误触查询 |
| 手势 / 三键返回 | 子页/弹层先返回本层；草稿离开走M02 |
| 减弱动画 / 快速连续操作 | 降低材质与位移负担；取消/防抖/幂等不依赖动画时长 |
| 统一字体 | 使用用户确认的 MiSans 家族和经核验的语义字重；工程核验字体文件、许可与缺字回退，不把 Figma 混字当规范 |

## 7. 交付与验证边界

本轮交付源稿与契约，验收场景全部为 `not-run`。作者自检仅验证JSON结构、ID/引用、图文契约一致性与覆盖；不宣称Miuix版本/API已验证，不宣称Mermaid已渲染，不宣称Android构建、模拟器、vivo Android12真机或WebDAV/OSS/APK已联调。

每个可审阅批次按“子Agent自检 → 总负责人总检 → 用户人工通过”。未通过时禁止依赖该批次的下游实施；不依赖它的规划可继续。新增可见名称和未决业务语义必须先问用户，不从内部标识或文稿的用途说明直接生成最终文案。
